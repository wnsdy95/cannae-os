# Skill-First Product Scope

Decision: USER, 2026-11-10. Active development is a document-driven skill/plugin
for existing AI clients, not a separate agent operations application.

This decision supersedes the previous eight-outcome program as the default
development queue. It does not declare those outcomes complete or delete their
code, requirements, failures or evidence. The [completion backlog](completion-backlog.md)
separates active core work from the retained platform program.

## Active Objectives

On 2026-11-15 the USER requested a new goal addressing remaining skill-level
limitations, while keeping dashboards and servers deferred. The active cycle is
**Skill Reliability And Efficiency**, R1-R6. It extends the completed baseline;
it does not reopen or reinterpret its twenty accepted requirements.

1. **R1 - Robust request intake and routing:** preserve original Korean/English
   requests, compound objectives, exclusions and declared authority while reducing
   known heading/wording-sensitive omissions and irrelevant reading.
2. **R2 - Efficient instruction and context delivery:** shorten ordinary entry
   guidance and select task-relevant reference sections without dropping required
   sources, conditional controls or history needed for the actual task.
3. **R3 - Source-grounded quality beyond rehearsed cases:** compare baseline and
   candidate behavior on a frozen authoring/review evaluation, including withheld
   tasks, false findings, compressed reports and original-source fidelity.
4. **R4 - Terminology and document-change impact:** make scoped term capture,
   proposed updates and affected-document reconciliation practical through local
   files/helpers, without automatic confirmation, disclosure or policy adoption.
5. **R5 - Repeatable cross-client work and recovery:** demonstrate complete
   document-only workflows with actual notices, rerouting, changed-source holds,
   useful partial work and cold-start receiving in both client directions.
6. **R6 - Reproducible maintenance and distribution:** retain exact evidence,
   test affected controls efficiently, diagnose stale skill copies and verify
   bounded compatibility in existing clients without changing host settings.

The [new acceptance inventory](completion-backlog.md#skill-reliability-acceptance)
has eighteen required criteria, separate from A01-A21. They started planned;
the backlog records evidence-backed changes, not inherited acceptance. Audit
and registration are not implementation. Ordinary CLI helpers and existing local
file workflows are in scope. A new service, dashboard, orchestration backend,
authenticated application or production infrastructure is not. Optional plugin
packaging remains deferred, not a requirement to ship this cycle.

### Completed Baseline Objectives

The USER confirmed these five objectives on 2026-11-10. They replaced
the previous eight-outcome program and reached bounded acceptance on 2026-11-15.
The unchanged definitions below preserve their original scope. Each required its own
behavioral acceptance; scope and entrypoint cleanup alone cannot complete an
objective. The [requirement audit](completion-backlog.md#requirement-level-audit)
retains their evidence and limits without changing these criteria.

1. **G1 - Document authoring and revision quality:** verify representative SOP,
   order, research and handoff tasks preserve intent, required work, sources,
   authority, explicit unknowns and revision history.
2. **G2 - Role-bounded routing and delegation:** verify required references are
   delivered without unnecessary context or expanded authority. Cover human/AI
   modes, stale or missing routes, capability gaps and provisional task cells.
3. **G3 - Complete working flow:** demonstrate request -> plan -> review/backbrief
   -> work -> report/handoff in existing clients without a dashboard or login.
   Check semantic omissions, bounded replanning, method changes, reporting,
   stop points, tool-failure handling and sensitive-output boundaries. Reuse
   applicable existing controls instead of building a separate execution service.
4. **G4 - Bounded self-improvement and corpus maintenance:** turn observed gaps
   and AAR findings into tested document, prompt and routing changes in both
   provider skills. Keep canonical sources, indexes and repository outputs
   coherent without self-authorizing scope, policy or release.
5. **G5 - Client distribution:** verify Codex/Claude installation, discovery,
   repository resolution and equivalent behavior. Add a thin plugin package
   only if needed; report whether it is included, tested or still unproven.

The product areas below describe what these objectives cover; they are not an
additional goal count. The backlog owns current evidence and next actions.

## Active Core

1. **Document authoring:** choose a useful format, preserve original intent and
   distinguish evidence, interpretation, assumptions and decisions. Maintain
   ownership, version/supersession, authority and handoff information.
2. **Document routing:** give the human efficient access without an artificial
   AI-role restriction; give delegated agents the references relevant to their
   role, department, task and authority.
3. **Agent work discipline:** support one agent and multiple agents through
   explicit tasking, backbriefs, bounded autonomy, reporting and handoffs.
4. **Corpus maintenance:** keep canonical documents, source maps, indexes,
   links and repository-specific outputs coherent.
5. **Bounded improvement:** use observed failures and AAR findings to improve
   documents, prompts and routes inside the user's scope. Mirror reusable
   procedure changes in both provider skills and test the affected behavior.
6. **Distribution:** maintain equivalent Codex and Claude skills. A plugin, if
   added, packages this same workflow; it does not require a new server product.
   Existing skill installation is not proof of a separately packaged plugin.

Use [Document Authoring Workflow](document-authoring-workflow.md) for ordinary
writing and maintenance. Local schemas, validators, receipts and CLI helpers
remain supporting tools where the selected workflow needs them.

## Deferred Platform Work

- Dashboards, command-post screens, browser polish and operational COP UI.
- Standalone operator login, approval UI, multi-user application and evidence API.
- Console-specific training evaluation and browser/crash acceptance campaigns.
- A separately operated orchestration service or always-running execution backend.
- Production gateways, distributed coordination, protected hosts/keys and
  independently operated monitoring infrastructure.

Do not pick one of these as the next task merely because an older roadmap or
failed platform check remains open. New development needs an explicit USER
scope decision. Retained documentation remains available for inspection and
specifically requested maintenance.

Deferral is not permission to clear an existing hold, replay a decision, bypass
an approval, disable a guard, stop a service or alter credentials. Already
admitted operations retain their original settlement and authority rules.
Actual delegated execution still requires its routing/preflight and applicable
tool controls. Ordinary document drafting is not evidence of execution.

## Core Acceptance

| Objective | Evidence required before closure |
| --- | --- |
| G1 | Representative requests create the right document with traceable claims, explicit unknowns, ownership and acceptance criteria; revisions preserve required intent and record changes. |
| G2 | Both providers deliver the required task documents in human and delegated modes; missing/stale/wrong-role cases and capability gaps are checked without expanding access or authority. |
| G3 | An observed complete workflow covers requirement checks, bounded changes, actual results, failure/stop decisions and a receiver-ready handoff without chat-memory dependence, a dashboard or application login. Actual tool execution is assessed separately from drafting. |
| G4 | An observed gap leads to a reusable improvement in both skills, relevant regression evidence and coherent source/index/history/output records; no new authority follows from a pass. |
| G5 | Installation/discovery and repository resolution work for both clients with equivalent rules; a copied skill is not misrepresented as the entire corpus or runtime. Optional plugin packaging has an explicit tested or deferred disposition. |

This is an acceptance list, not five newly completed features. Record the checks
actually run and residual work in the backlog. Report passed/total criteria
only after reviewing that fixed denominator. Do not use the old 125-candidate
inventory percentage as skill/plugin completion, remove deferred candidates
to inflate progress, or equate inventory coverage with task-level correctness.

## Continuation Rule

For "continue" or "what next", read this scope and the active backlog first.
Choose the smallest dependency-ready R1-R6 task and its SR acceptance criterion.
Do not reuse the completed A-series denominator or carry its passes into the new
cycle. Existing exact decisions stay attached to their artifacts; the prior
until-completion verification consent ended with that goal. Obtain new applicable
consent before a native model transfer; registration is not transfer approval.
Consult the implementation
registry for existing code and claims, not as permission to expand the product.
If a core task appears to require a deferred service, identify the actual
dependency and return the scope decision to the USER rather than silently
building that service.

This is a project decision and local engineering policy, not a new claim about
military doctrine or a change to executable authorization contracts.
