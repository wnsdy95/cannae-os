# Subject-Bound Workload Controls

## Boundary

A routed fixture suite verifies framework code. Even a receipt bound to a report
digest does not establish that the child inspected that report. A retained
synthetic function probe on `1f2b261` passed the actual routed document-access
fixture for both clean and credential-bearing report inputs; its child received
only a static script path, not either payload. This demonstrated an input-flow
gap, not full report admission or an external disclosure exploit.

The local corrective candidate adds a separate mandatory policy worker to actual
`recordWave`. All new report admissions run it before existing framework
regression controls; neither class substitutes for the other. There is no
caller-controlled skip, timeout increase or model call. No program outcome is
closed by this core-pattern guard.

## Exact Subject

The controller verifies the repository namespace, complete report, actual agent
context references and every unique same-mission/wave work-evidence reference.
It opens regular files through bounded reads, rejects symlink components, checks
exact hashes and strict UTF-8, and rejects NUL/binary data. Limits are 1 MiB report,
2 MiB per file, 4 MiB decoded evidence, 64 evidence files, 8 MiB encoded input,
64 JSON nesting levels and 100,000 JSON nodes. Overflow is a hold, never silent
truncation. These are local checks, not race-proof filesystem isolation.

`WorkloadControlInput` binds canonical report input, exact evidence bytes,
agent/context hashes, repository identity/state, source fingerprint, manifest
observation and a fresh 128-bit invocation nonce. Raw input crosses only local
stdin to a fixed Node worker; the controller does not persist that input or raw
stdout/stderr. Existing work artifacts remain in their original store.

The worker has a fixed 10-second deadline, bounded output and heap, no shell and
no inherited provider credentials or Node injection flags. It uses the existing
OPSEC linter for known credential patterns and explicit restricted markings.
Its `WorkloadPolicyAssessment` retains only bounded finding codes, subject indices
and hashed locations. Findings beyond 128 remain counted and keep the decision
blocked. It does not echo values, excerpts, raw paths or raw agent/context IDs.

The parent validates output structure, exact purpose, nonce, complete input hash
and scope, exit outcome, repository state and policy-source fingerprint. The
digest-derived `WorkloadControlReceipt` retains this observation separately from
`ControlExecutionReceipt` v0.2 framework regressions. Both remain non-authorizing.

## Admission And Recovery

Freeze the report and work references before invoking the existing skill
`report` command. The controller selects `workload_control_receipt_refs` itself.
An additive optional field preserves parsing of historical v0.1 reports; absence
is permitted in an input draft, not in a newly persisted report. Neither generated
receipt list changes the canonical report input hash. No agent-issued receipt
list or claim can satisfy the worker.

Blocked/failed worker observations remain retained without a report or SITREP.
Capture/contract failures before spawn reject admission without fabricating an
execution receipt. Review
the digest-only finding and original access-controlled evidence separately.
Any redaction/replacement needs reviewed new work and a fresh report ID, followed
by fresh admission. Never edit retained evidence/receipts or waive the gate.
Binary/oversized outputs need a separately reviewed bounded textual representation;
do not claim an uninspected attachment was cleared.

After all existing framework controls, publication rebuilds the current subject
from exact stored work bytes and rechecks target and source state. Its own receipt
append does not invalidate the subject, but changed work, report, target or policy
does. Exact admitted retries may reuse only their original manifest-backed passing
receipt under those same bindings. Legacy reports remain readable; missing
workload evidence cannot authorize new publication. No original task is replayed.

## Limits And Verification

This is a local, deterministic core-pattern check, not universal secret detection,
custom mission EEFI evaluation, semantic truth, CCIR/KM/resource assessment,
authenticated release review, sandbox attestation or an exclusive gateway. The
existing linter can have false positives/negatives; audited exceptions and broader
input-bound controls remain open. A clean result is not external release approval.
Metadata, including wrapped workload records, is never task evidence.

Run `node run-workload-control-fixtures.js`, generic validator fixtures, mission
lifecycle/metadata fixtures and both skill/routing checks from one frozen source.
The workload fixtures exercise real controller rejection before framework
regressions and a real bounded child pass; the lifecycle suite covers clean report
publication and exact retries. Synthetic sample receipts are structural examples,
not records of executed work.

Expensive framework suites still run per admission with their unchanged 600,000 ms
production timeout. Purpose-separated, source-qualified regression caching and
complete workload-policy adapters remain separate work; this guard does not
claim their latency or coverage problem is solved.
